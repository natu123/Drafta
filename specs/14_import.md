# Obsidianからの取り込み

採用日: 2026-10-08. D1〜D5はGlesさんの承認により推奨案で確定しました.
2026-10-08の本番短縮確認 (保存履歴の記録と別Memoへの復元) の合格後に実装し, 0.6.0として公開準備中です (2026-10-09時点で未Deploy).

## 目的と範囲

- ObsidianのVault (Markdownファイルの集まり) を, DraftaのTray･Memoとして取り込みます.
- 初回は文章だけを対象とします. 画像･添付ファイル･Memo間リンクは取り込まず, 取り込めなかった要素を結果画面で知らせます.
- 取り込みは新しいTrayへの追加だけです. 既存のTray･Memoを上書き･統合しません.
- Notion･Evernoteは後続です. 今回作る共通部分 (読込･検証･プレビュー･一括保存･結果通知) を再利用します.

## 決定事項

各項目は「推奨」の案を採用しました. 他の案は検討記録として残します.

### D1. ファイルの選び方

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A (採用) | Vaultのフォルダを選択 (複数の`.md`選択も可) | 新しい依存ライブラリが不要です. Obsidianの保存形式そのままです. | スマホのブラウザーではフォルダ選択が使えない場合があります. |
| B | Vaultをzipにして選択 | スマホでも選べます. Notionの書き出し (zip) と入口を共通化できます. | zip展開用の依存 (例: fflate) を追加します. 利用者がzipを作る手間があります. |
| C | AとBの両方 | 利用者が選べます. | 初回の実装と検証が増えます. |

zip対応はNotion対応時に追加する想定です.

### D2. フォルダとTrayの対応

DraftaのTrayは1階層です.

| 案 | 内容 |
|---|---|
| A (採用) | 最上位フォルダごとに新しいTray「Vault名 / フォルダ名」を作ります. Vault直下のファイルはTray「Vault名」へ入れます. 2階層目以下のファイルは, 最上位フォルダのTrayへまとめます. |
| B | すべてを1つの新しいTray「Vault名」へ入れます. フォルダ構成は失われます. |
| C | すべてのフォルダを, パス名のTray (例:「Vault / 仕事 / 2026」) にします. Trayの数が多くなります. |

### D3. Obsidian固有の書き方

| 要素 | 採用する扱い |
|---|---|
| `[[ノート名]]`, `[[ノート名|別名]]` | Drafta内リンクがないため, 表示名の文字として残します. |
| `![[画像.png]]`, `![](画像.png)` (埋め込み) | 取り込まず, 本文に`[画像: 画像.png]`の文字を残します. 結果画面で件数を知らせます. |
| 先頭のFrontmatter (`---`で囲むYAML) | 本文から外します. `tags`は本文末尾へ`#タグ`の文字として残します. |
| `#タグ` (本文中) | 文字のまま残します. |
| Callout (`> [!note]`) | 引用として取り込みます. 種別名は先頭の文字として残します. |
| `==ハイライト==` | 記号を外した通常の文字にします. |
| 数式･Mermaid･Dataview | コードブロックとして文字のまま残します. |
| Markdownリンク `[文字](URL)` | http･https･mailtoだけリンクにします. それ以外は文字として残します. |

### D4. 入口のUI

AGENTS.mdの「UI変更は案を示して合意後に実装」に従い, 3案を示します.

| 案 | 場所 | 考え方 |
|---|---|---|
| A (採用) | 設定ダイアログに「データ」区分を新設し,「インポート」を置く | 後続の手動バックアップ･書き出しも同じ場所へ集められます. |
| B | アカウントメニューに「インポート」を追加 | データがアカウントに属することと合います. メニューが長くなります. |
| C | Tray一覧の作成メニューに「取り込んで作成」を追加 | 作成操作の近くにあり見つけやすいです. 一覧のUIが複雑になります. |

### D5. 大きすぎるMemo

1 Memoの保存上限は約450KBです (`CLOUD_LIMITS.documentBytes`).

- A (採用): 上限を超えるファイルは取り込まず, 結果画面でファイル名を知らせます.
- B: 上限内に分割し,「元の名前 (1/3)」のように複数Memoにします.

## 取り込みの流れ

1. ファイルを選ぶと, 端末内だけで読み込みと変換を行います. この段階ではサーバーへ保存しません.
2. プレビューで, 作成するTrayとMemoの数, 取り込めない要素 (画像･大きすぎるファイル･非対応形式) の一覧を表示します.
3. 利用者が確定した場合だけ保存します. キャンセル時はデータを残しません.
4. 保存は既存の保存層を使い, 1回400 Memo以内に分けて行います (`CLOUD_LIMITS.changedNotes`). 途中で失敗した場合は, 保存済みと未保存の件数を示し, 未保存分だけ再試行できるようにします.
5. 結果画面で, 作成したTray･Memo数と取り込めなかった要素を示します.

## 安全性

- 確認した事実: 既存の`plainMarkdownToRich`は, 本文中のHTMLタグを無害化せずに通します (`Drafta_Web/src/lib/utils.ts`の`processInline`). Drafta自身が書いたMarkdown向けの変換器のためです.
- そのため, 外部ファイルは既存の変換器へ直接渡しません. 取り込み専用の変換で, HTMLタグを文字として扱い, リンクのURLを検査してから, 文書の検証 (`document-codec`･`workspace-backup`の検証) を通します.
- 件数の上限 (全体1万Memo･1000 Tray) を, 既存分と合わせて保存前に確認します. 超える場合は保存を始めません.
- 日時: ファイルの最終更新日時を, Memoの作成日時と更新日時に使います.

## 費用への影響 (要再確認)

- 取り込んだMemoの数だけFirestoreへの書き込みが発生します. 保存履歴が新規Memoの初回版を記録する場合, 書き込みはおよそ2倍になります.
- 無料枠 (Spark) の1日あたりの書き込み上限に近づく可能性があります. 上限値は実装前に公式資料で確認します. 取り込みMemoの初回版を履歴へ記録するかも, あわせて決めます.

## 検証の計画

- 変換: 見出し･リスト･チェックリスト･表･コード･引用･Callout･Wikiリンク･埋め込み･Frontmatter･HTMLタグ入りの試験用Vaultで, 変換結果のテストを作ります.
- 保存: ローカルEmulatorで, 400件を超える取り込み, 途中失敗からの再試行, 上限超過の拒否を確認します.
- 画面: 1440px･375pxでプレビューと結果画面を確認します.
- 公開: 利用者に影響する更新のため, Version (0.6.0の想定), 11言語の更新履歴とLanding-pageを揃えて公開します.

## 実装と検証結果 (2026-10-09)

- 変換･取り込み計画は`Drafta_Web/src/lib/obsidian-import.ts`, 画面は`import-dialog.tsx`と設定Dialogの「データ」区分です. 保存完了の待機は`cloud-session.tsx`の`saveWorkspace`です.
- 安全側の既定: 埋め込みの表示名 (`[画像: 名前]`) は表示中の言語に合わせます. 入れ子のリストは既存の変換器と同じく1段にします. 取り込んだMemoも通常どおり保存履歴の初回版を記録します. 生のファイルが2MBを超える場合は読み込まずに除外します.
- 分割は350件･7MBを上限とし (`CLOUD_LIMITS`の400件･8MBに余裕を持たせる), 各回の保存完了を待ちます.
- 単体テスト12件 (変換･Tray対応･上限･801件の分割保存と失敗後の再開) が成功しました. Java 21導入後, Emulatorで801件の分割保存テスト (`npm run test:storage`) とルールテストが成功しました. localhost:9002の1440px･375pxで, フォルダ選択 → プレビュー (除外ファイルと理由) → 保存 → 結果 → 再読み込み後の保持を確認しました. HTMLタグは文字として表示され, 実行時エラー･横スクロールはありませんでした. 確認中に見つけたフォルダ選択属性の不具合は修正済みです.

## 今回の範囲外

- 画像･添付ファイルの保存 (Firebase Storageの導入と費用の承認が別途必要です).
- Memo間リンク, 同じVaultの再取り込み時の重複判定と差分更新.
- Notion･Evernoteの取り込み.
