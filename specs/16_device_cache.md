# 端末キャッシュと起動時の差分読み込み

採用日: 2026-10-21. Glesさんの承認 (メモの内容を端末に保存すること) により, 0.7.0で実装します. 続いて, 以前の状態の復元を0.7.1, 要約と本文の分離 (保存形式の変更と本番データの移行, 別途承認) を0.8.0で扱います.

## 背景

- アプリを開くたびに, サーバーから全メモを読み直していました. Vault取り込み後 (558メモ) は1回あたり約10.3MB (本文の文字は3.6MB, 残りは文書の構造) で, 本番では約3秒がデータの受け取り待ちでした. 画面側の重い処理はありませんでした.
- 読み取り回数も, 開くたびにメモの件数分 (約560回) かかります.
- Notion等は, 端末に保存した前回のデータをすぐ表示し, サーバーからは変わった分だけを受け取ります.

## 速さの調整 (0.8.6, 2026-10-23)

Glesさんの報告「iPhoneのPWAを何回か開いて一覧をスワイプして閉じていると, 1秒くらいスワイプが効かないことがある」への対応です. Emulator (390pxタッチ, CPU 4倍減速, すべてのメモ559件, 端末キャッシュあり) で起動を繰り返して計測しました.

- 原因: メモの並べ替え (dnd-kit) のタッチ処理が画面全体のタッチの動きを待たせるため, 長い処理の間はスワイプも止まります. iPhoneは起動中に前回の画面の写真を見せるので, 一覧が出る前の処理も「見えているのに動かない」時間になります.
- 一覧が出る前の処理 (Profile, 4倍): 約0.84秒→約0.49秒. 全本文の検証 (約0.63秒) と凍結を一覧の後に回し (上の採用仕様の「検証」), プレビューは全文ではなくカードに出す先頭300字だけを読みます (約0.31秒→約0.07秒). 全文は検索するときに初めて, メモごとに1回だけ作ります (`global-search.ts`). 残りの大半はキャッシュのJSONの読み込み (約0.33秒) です.
- 一覧が出た後: 一覧に触れている・スクロールしている間と, その後0.3秒は残りのカードを足すのを待ちます. 連続でスワイプしている6秒間の長い処理は13回→1回, 最も遅いスワイプは約0.27〜0.37秒→約0.18〜0.2秒でした. まだ描いていない場所は, 薄いカードの形で見せます.
- 壊れた本文の扱い: キャッシュの本文を1つ壊して起動し, 一覧が出た後に写しを捨ててサーバーから読み直し, 正しい写しを書き直すことを確認しました (エラーなし).
- 計測上の注意: 並行して動いていた他のSessionのBuildやテストでPCが混んでいたため, 起動全体の時間はぶれが大きく, Profileの内訳で比べました. Emulatorでは保存形式の更新の直後だけ, 起動時の監視が全要約を受け取り直します (約0.4秒). 実際の使い方に合わせ, 計測の前に1回保存しておきます.

## 速さの調整 (0.8.5, 2026-10-22)

Glesさんの「大手サービス並みのレイテンシーにしたい」という方針で, 0.8.4と同じ環境 (本番用Build+Emulator, Vault約560メモ, PC) で続けて直しました. CPUの4倍減速 (iPhone相当の目安) でも測り, 0.8.4と0.8.5を同じ手順で比べました. 「最初の表示」は操作から次の描画までです.

| 操作 | 0.8.4 (1倍 / 4倍) | 0.8.5 (1倍 / 4倍) |
| --- | --- | --- |
| 328件のTrayへの切り替え (最初の表示) | 約0.2秒 / 約1.2秒 | 約0.075秒 / 約0.2秒 |
| 同 (全件の描画) | 約0.23秒 / 約1.3秒 | 約0.3秒 / 約1.8秒 (操作は止めない) |
| メモを開く (最初の表示) | 約0.18〜0.27秒 / 約1.0〜1.3秒 | 約0.07〜0.12秒 / 約0.28〜0.67秒 |
| 打鍵から次の描画まで (中央値) | 13ms / 28ms | 19ms / 30ms (差は1フレーム以内) |

- Trayの一覧: 開く側 (チャットは最下部, ToDoは先頭) に近い24件だけを先に描き, 残りは40件ずつフレームの合間に足します (Reactのtransitionで, 操作があれば譲る). 未描画のカードは実寸 (余白込みで74px, 本文なし70px, 区切り40px) の空きで確保するので, 読んでいる位置もスクロールバーも動きません. 折りたたんだピンは最後に描き, ドラッグ中は足しません. PCとスマホ (390px, タッチ) の4倍減速で, 足している間に上へスクロールしても読んでいるカードが0px動かないこと, 最下部から開くこと, 足している間のタップで開くことを確認しました.
- メモのカード: 開いたメモと選択の変化では, 変わった2枚だけを描き直します (カードをReact.memoにし, 全体の状態を渡さない).
- メモを開いても保存しません. 開いた時刻 (`lastAccessedAt`) を更新していましたが, 表示にも並び順にも使っていませんでした. 0.8.4の「開いた時刻の保存の準備」もなくなります.
- エディター: TipTapの`EditorContent`は, ReactのNode-viewのために, 開くたびに本文のDOMをもう1回作り直し, 閉じるときにもう1回作り直していました (4倍で計約0.12秒). このアプリにReactのNode-viewはないので, 作ったViewをそのまま差し込む部品に替えました. エディターは最初の描画で作り (`immediatelyRender`. 本文を開いた状態で事前描画するページはない), 閉じている色パレットのボタンは描きません. 取り消しの履歴はこれまでどおりメモごとです.
- 読み込み直後の最初の保存: 本文の大きさを知るために全本文を文字列にしていました (4倍で約1.2秒の固まり). 大きさは本文を読んだとき, または読み込みの1秒後から8msずつ測り, 読み込んだまま変わらないメモは読み込んだものをそのまま使います (同約0.28秒).
- 計測上の注意: Event Timingのキーの時間は, この環境では保存の表示が変わるまで確定せず, 数秒に見えました. Traceでは打鍵から表示まで約35ms (4倍) です. ベンチマークは打鍵から次のフレームまでをページ内で測ります. また, PlaywrightのChromeでは操作の後にAccessibilityの更新 (4倍で約70ms) が走ります.
- 残り: 入力が止まったときの保存の準備 (4倍で約0.2秒, 1倍で約0.05秒. 編集中のメモのHTMLを文書に変換する処理と全体の検証) と, メモを開くときのエディター生成 (4倍で約0.1秒) です.

## 速さの調整 (0.8.4, 2026-10-22)

Glesさんの「起動直後, 画面は出るのに0.2秒ほど操作が効かない」という報告を, 本番用Build+Emulator (Vault 562メモ, PC) で計測して直しました.

- 起動時に, 確定済みのワークスペースを丸ごと複製 (structuredClone, 約9MB) して監視の基準とキャッシュの書き込みに渡していました (約0.37秒). 読むだけなので複製をやめました.
- サーバーと同じ版でも起動のたびにキャッシュを書き直し, そのたびに全体を検証し直していました. 同じ版なら書かず, 検証済みのワークスペースは文字列にするだけにしました. 書き込みは求めてから2秒以上後にし, 操作の直後に重ならないようにしました.
- 結果: 一覧が出るまで約1.39秒→約0.75秒, 一覧が出た直後に操作を塞ぐ処理 (0.12〜0.15秒) は0件.
- メモ一覧のカードは, 1行の抜粋に本文全部の文字を入れていました (328件のTrayで約138万字). 先頭300字にし, 画面外のカードは描画を省きます (`content-visibility`, 見積もりの高さは実際の66px/62px). 328件のTrayへの切り替えは約1.05秒→約0.25秒 (操作を塞ぐ最長の処理0.8秒→0.14秒), 40件は約0.2秒→約0.12秒です. チャットスタイルで最下部から開く位置は, カードの高さが落ち着くまで数フレーム確かめ直します.
- メモを開いたときの保存 (開いた時刻) の準備で, 全メモの要約を毎回作り直していました. 本文ごとにタイトルと抜粋を覚え, 抜粋は先頭だけを読み, 大きさの確認も文字数で足りるときは数えません. 開く時間の保存の準備 (約0.11秒) がなくなりました.

## 採用仕様

- 保存先: ブラウザーのIndexedDB (データベース`drafta-cache`). アカウント (UID) ごとに1件とし, 他のアカウントのキャッシュは読みません.
- 保存内容: サーバーで確定した状態 (版番号, 設定, トレイ, 全メモ) と, その版の保存時刻の下限 (`since`). 保存待ちの未確定の編集は含めません.
- 起動時: キャッシュがあれば, サーバーを待たずに表示します. 裏でサーバーのワークスペースの版を1回読み, 同じ版ならそのまま使います (読み取り1回). 版が進んでいれば, `since`以降に更新されたメモだけを読み, キャッシュに重ねます. 削除はワークスペースのメモの並び順から判定します. 足りないメモがある, キャッシュが壊れている, 検証に通らない場合は, 従来どおり全メモを読みます.
- 起動直後の編集: サーバーの確認より先に編集した場合も, 保存キューの統合 (他端末の更新と同じ仕組み) で扱います.
- `since`: 起動時にサーバーから読んだワークスペースの保存時刻だけを使い, そのセッション中は変えません. 1回の保存の各メモはワークスペースと同じ保存時刻を持ち, 後の保存は必ず新しい時刻を持つため, 実際より古い`since`は読み取りが少し増えるだけで, 取りこぼしません. 新しすぎる`since`は取りこぼしの原因になるため使いません.
- 書き込み: 起動時の確定後と, 自分の保存や他端末の更新が確定した後に更新します. 大きなワークスペースで入力を妨げないよう, 書き込みは最短10秒の間隔にまとめ, 画面が非表示になるときにも行います. 書き込みに失敗しても動作は続けます (次回は全メモを読みます).
- 削除: ログアウトしたら, そのアカウントのキャッシュを消します. 認証の失効 (再ログインで復旧する場合) では消しません.
- 検証: キャッシュは読み込み時に, 本文以外 (設定, トレイ, メモの項目と親子関係) を保存時と同じ検証に通します (`parseCachedWorkspaceBackup`). 本文は一覧を表示した1秒後から8msずつ同じ検証 (`documentValue`) に通し, 凍結します (`settleDocumentsLater`). メモを開く前と保存する前には, まだの本文をその場で検証します (`trustDocument`). 通らない本文があれば, キャッシュを捨ててサーバーから読み直します (0.8.6. それまでは読み込み時に全本文を検証しており, スマホで一覧が出る前に約0.5秒かかっていた).
- 対象外: オフラインでの編集の保存, 未保存の編集の永続化, 端末間でのキャッシュの共有は行いません (従来どおり).
- 変更しないもの: Firestoreの保存形式, Firestoreルール, Index.

## 注意

- メモの内容が端末 (ブラウザーの保存領域) に残ります. 共用の端末では, 使い終わったらログアウトしてください. ブラウザーのサイトデータの削除でも消えます.

## 検証

- 単体: キャッシュの保存･読み込み･アカウントごとの分離･壊れたデータの破棄.
- Emulator: 差分読み込みが, 同じ版･他端末の編集･追加･削除･並べ替え･トレイ変更のあとで全件読み込みと一致すること. `since`が古くても一致すること.
- 画面: キャッシュからの表示, サーバーとの差分の反映, 起動直後の編集, ログアウトでの削除. 起動時間と読み取り回数を修正前後で比べます.

## 実装と計測 (0.7.0, 2026-10-21公開)

- 実装: `cloud-workspace.ts`の`loadWithSince`･`loadSince` (差分読み込み), `workspace-cache.ts` (IndexedDBへの保存と書き込みの間隔の調整), `cloud-session.tsx` (起動時の流れ, 確定した版が変わるたびの書き込み予約, 画面非表示での書き込み, ログアウトでの削除).
- Emulatorテスト: 差分読み込みが, 同じ版 (読み取り1回で同じ内容)･他端末の2回の保存 (編集･削除･追加･並べ替え･トレイ名変更とメモ移動)･古い`since`･メモの欠けたキャッシュ･他アカウントのキャッシュのいずれでも全件読み込みと一致することを確認しました. 単体テストでキャッシュの保存･分離･破棄と書き込みの間隔を確認しました.
- 画面 (Emulator, 549メモの取り込み後): キャッシュ (8.7MB) が保存され, 閉じている間の他端末の追加･削除が開き直すと反映され, 開いた直後の編集が他端末に届き, ログアウトでキャッシュが消えることを確認しました.
- 本番の計測 (GlesさんのPCのChrome, 約560メモ): 一覧が出るまで, キャッシュなし4.87秒 → キャッシュあり1.78秒･1.81秒 (約0.37倍). 「保存済み」まで2.36秒･2.32秒.
- 残りの時間の内訳 (Emulator): ページの読み込みとログインの確認 約0.3秒 (本番は約1秒), キャッシュの読み込み 約26ms, 検証 約170ms, 全メモの本文を画面用 (HTML) に変換する処理 約800ms, 描画 約180ms. 変換は, 0.8.0の要約と本文の分離 (一覧は要約だけ, 本文は開いたときに変換) で解消する予定です.
